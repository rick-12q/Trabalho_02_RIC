\vspace{5mm}
\section{Programação}
\label{sec:programacao}

O desenvolvimento do sistema envolveu principalmente três partes: a programação do ESP32, a implementação da comunicação através da API REST e a construção da interface de supervisão utilizando Node-RED. Além disso, foi implementada a atualização remota do firmware utilizando OTA.

Para facilitar a organização dos diferentes componentes desenvolvidos, o repositório foi dividido em diretórios específicos para cada parte do sistema. Sua estrutura principal é apresentada a seguir:

\begin{repobox}
	Trabalho\_02\_RIC/
	|
	+-- Code/
	|   |
	|   +-- backend/          
	|   |
	|   +-- firmware/         # Código do ESP32 (.ino)
	|   |
	|   +-- frontend/         
	|   |
	|   +-- simulator/        
	|   |
	|   +-- README.md         
	|
	+-- Node\_red/
	|   |
	|   +-- Node\_red.json     
	|
	+-- ...
\end{repobox}

O firmware utilizado no ESP32 encontra-se no diretório \texttt{Code/firmware/}, enquanto o fluxo desenvolvido no Node-RED está disponível em \texttt{Node\_red/Node\_red.json}. Os demais diretórios presentes em \texttt{Code/} estão relacionados aos recursos adicionais implementados no projeto, incluindo a API, o simulador e a interface web.

\vspace{3mm}
\subsection{Programação do ESP32}

O firmware do ESP32 foi desenvolvido em C++ utilizando o framework Arduino. O programa é responsável pela leitura do BME280, leitura do botão, controle do LED, atualização do display OLED, conexão com a rede Wi-Fi, comunicação HTTP e funcionamento do OTA.

Para implementação disso, foram utilizadas bibliotecas específicas para comunicação Wi-Fi e HTTP, além daquelas em uso para o BME280, display OLED e atualização OTA.

O sensor BME280 foi conectado através do barramento I$^2$C. Durante a inicialização do dispositivo, o firmware tenta localizar o sensor inicialmente através do endereço \texttt{0x76}. Caso não seja encontrado, também é realizada uma tentativa utilizando o endereço \texttt{0x77}.

Após a inicialização, são realizadas leituras periódicas de temperatura, umidade e pressão atmosférica. 

O botão foi configurado utilizando uma entrada digital com \texttt{INPUT\_PULLUP}. Dessa forma, o estado lógico do pino é alterado quando ocorre o acionamento físico do botão. Essa informação é enviada juntamente com os demais dados adquiridos pelo ESP32.

O LED foi configurado como saída digital e representa o atuador utilizado no projeto. Diferentemente das informações do BME280, que seguem do ESP32 para o sistema de supervisão, o estado desejado para o LED é recebido através da comunicação com a API.

Para facilitar o acompanhamento do dispositivo durante os testes, também foi utilizado o display OLED presente no módulo. Nele são apresentados os valores obtidos pelo BME280, o endereço IP do ESP32 e os estados do botão e do LED.

A comunicação com a rede é realizada através do Wi-Fi. Durante a inicialização, o ESP32 tenta estabelecer conexão com a rede configurada e, após a conexão, passa a realizar as requisições HTTP necessárias para funcionamento do sistema.

O firmware também possui uma rotina de reconexão. Caso a conexão Wi-Fi seja interrompida durante a execução, novas tentativas são realizadas sem que seja necessário reinicializar manualmente o dispositivo.

Para evitar uma quantidade excessiva de requisições, foram definidos intervalos para cada operação. O envio da telemetria é realizado aproximadamente a cada cinco segundos, enquanto a consulta do estado do LED ocorre aproximadamente a cada dois segundos.

\subsection{Comunicação através da API REST}

A comunicação entre o ESP32 e o Node-RED foi realizada utilizando uma API REST. Essa estrutura permite organizar diferentes operações através de rotas HTTP, separando o envio das informações dos sensores das operações relacionadas ao atuador.

No envio da telemetria, o ESP32 realiza uma requisição contendo as informações adquiridas. Entre os dados enviados estão o identificador do dispositivo, temperatura, umidade, pressão e estado do botão.

Para o controle do LED é utilizado o processo contrário. O estado solicitado pelo usuário através do Node-RED é disponibilizado pela API e consultado periodicamente pelo ESP32. Após receber a informação, o firmware atualiza o estado da saída correspondente.

Entre as rotas utilizadas durante o funcionamento do sistema estão:

\begin{table}[H]
	\centering
	\caption{Principais rotas utilizadas na comunicação REST.}
	\label{tab:endpoints-api}
	\begin{tabular}{|c|p{5.3cm}|p{6.2cm}|}
		\hline
		\textbf{Método} & \textbf{Rota} & \textbf{Função} \\ \hline
		
		GET &
		\texttt{/health} &
		Verificação do funcionamento da API. \\ \hline
		
		POST &
		\texttt{/api/telemetry} &
		Recebimento das informações enviadas pelo ESP32. \\ \hline
		
		GET &
		\texttt{/api/telemetry/latest} &
		Consulta das informações mais recentes. \\ \hline
		
		GET &
		\texttt{/api/actuators/led} &
		Consulta do estado solicitado para o LED. \\ \hline
		
		POST &
		\texttt{/api/actuators/led} &
		Alteração do estado do LED através da interface. \\ \hline
		
	\end{tabular}
\end{table}

A utilização dos métodos GET e POST permitiu implementar tanto operações de consulta quanto operações de envio e alteração de informações. Dessa maneira, foi possível estabelecer a comunicação necessária para aquisição e atuação utilizando o mesmo padrão REST.

Durante os testes, as respostas HTTP também foram utilizadas para verificar o resultado das requisições. Isso foi importante principalmente durante a integração com o ESP32 físico, pois permitiu diferenciar falhas de conexão de requisições recebidas corretamente pelo servidor.

\subsubsection{Entrada dos dados}

A entrada e o processamento dos dados no Node-RED são realizados pelo grupo de nós denominado \textit{INPUT DATA}. Nesse grupo, foi implementado um nó \textit{HTTP IN}, identificado como ``ESP32 - Receber Telemetria'', configurado para receber requisições do tipo POST por meio da rota \texttt{/api/telemetry}. Os dados recebidos são estruturados em formato JSON, contendo informações como temperatura, umidade, pressão atmosférica, estado do botão e identificação do dispositivo.

Além da entrada por POST, o fluxo possui uma consulta periódica à API REST. Um nó temporizador, configurado com intervalo de dois segundos, inicia a requisição HTTP para obtenção dos dados mais recentes. A resposta é encaminhada ao nó ``JSON Converter'' e, posteriormente, à função ``Processar Telemetria'', responsável por separar e converter os valores recebidos antes de encaminhá-los aos demais grupos do fluxo.

\subsubsection{Exposição dos dados obtidos}

Após a chegada e o tratamento dos dados no \textit{flow} do Node-RED, estes são encaminhados, por meio de nós \textit{link}, ao grupo denominado \textit{INDICADORES}. Nesse grupo, blocos do tipo \textit{function} realizam a separação e preparação individual das variáveis de temperatura, umidade, pressão e estado do botão.

Cada função atribui ao \texttt{msg.payload} o valor correspondente à variável que será apresentada. Em seguida, os dados de temperatura, umidade e pressão são encaminhados aos respectivos elementos \textit{gauge} do dashboard, enquanto o estado do botão é convertido para uma indicação textual, permitindo identificar se este se encontra pressionado ou não. Dessa forma, os dados recebidos são organizados e apresentados individualmente na interface de monitoramento.

\subsubsection{Status de conexão}

O status de conexão é verificado periodicamente pelo Node-RED por meio do grupo \textit{STATUS DE CONEXÃO}. Um nó temporizador inicia a verificação em intervalos regulares, realizando uma requisição HTTP à API REST de acordo com a fonte de dados selecionada no sistema.

A resposta da requisição é analisada por blocos \textit{function}, que verificam se houve comunicação com o dispositivo ativo. A partir desse resultado, o fluxo determina o estado da conexão e atualiza as informações utilizadas pelo dashboard.

\subsection{Realização do OTA}

Além da comunicação REST, outro requisito do trabalho foi a implementação da programação remota do ESP32 utilizando OTA (\textit{Over-the-Air}).

A utilização desse recurso permite atualizar o firmware através da própria rede Wi-Fi. Dessa maneira, após a configuração inicial, não é necessário conectar fisicamente o ESP32 ao computador sempre que uma nova versão do programa precisar ser enviada.

Para implementação foi utilizada a biblioteca \texttt{ArduinoOTA}. Durante a inicialização do firmware são configurados os parâmetros necessários para identificação e autenticação do dispositivo na rede.

No firmware foi definido um \textit{hostname} para facilitar a identificação do dispositivo. Também foi configurada uma senha para impedir que a atualização seja realizada sem autenticação.

Durante o processo de OTA também foram configuradas funções responsáveis por indicar o início da atualização, seu progresso, finalização e possíveis erros. Essas informações permitem acompanhar a transferência e verificar se o novo firmware foi recebido corretamente.

Após a configuração inicial foram realizados testes de atualização através da rede. A Figura \ref{fig:ota-success} apresenta um dos testes realizados com sucesso.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.7\textwidth]{2-imagens/OTA succes.jpeg}
	\caption{Atualização remota do firmware através de OTA realizada com sucesso.}

A implementação do OTA se mostrou útil durante o próprio desenvolvimento do trabalho, uma vez que alterações posteriores no firmware puderam ser enviadas sem a necessidade de conectar novamente o cabo de programação ao ESP32.

\subsection{Desenvolvimentos extras}

Após a implementação dos requisitos principais do trabalho, foram desenvolvidos recursos adicionais com o objetivo de ampliar o sistema. Esses recursos não são necessários para realizar a comunicação REST entre o ESP32 e o Node-RED nem para o funcionamento do OTA, sendo portanto considerados desenvolvimentos extras.

\vspace{3mm}
\subsubsection{Simulador do ESP32}

Como primeiro desenvolvimento adicional, foi criado um simulador do ESP32 utilizando Python. Sua finalidade foi permitir a execução de uma fonte virtual de dados sem depender permanentemente do dispositivo físico.

O simulador reproduz parte do comportamento do ESP32, gerando valores correspondentes às variáveis ambientais e mantendo estados virtuais para o botão e para o LED. Para diferenciá-lo do dispositivo real, foi utilizado um identificador próprio.

A utilização do simulador também facilitou alguns testes durante o desenvolvimento, principalmente quando o ESP32 físico não estava conectado.

A Figura \ref{fig:simulador-extra} apresenta o simulador em execução.

\begin{figure}[H]
	\centering
	\includegraphics[width=0.7\textwidth]{2-imagens/print_simulador.png}
	\caption{Simulador do ESP32 desenvolvido como funcionalidade adicional.}
	\label{fig:simulador-extra}
\end{figure}

Para permitir a utilização tanto do dispositivo real quanto do simulador, foi adicionada uma seleção de fonte. O ESP32 físico é identificado como \texttt{esp32-001}, enquanto o simulador utiliza \texttt{esp32-simulator-001}. Assim, o usuário pode definir qual das duas fontes deseja utilizar durante os testes.

Cada registro contém informações referentes ao evento ocorrido, permitindo acompanhar alterações no estado da conexão, comandos enviados ao LED, mudanças no estado do botão e demais atividades relevantes durante a execução do sistema.
