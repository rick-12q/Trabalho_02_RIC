\section{Dificuldades e impressões}
\label{sec:dificuldades}

Durante o desenvolvimento do trabalho foram encontradas algumas dificuldades relacionadas principalmente à integração entre os diferentes componentes. Individualmente, o funcionamento do simulador, backend, banco de dados e interfaces era relativamente simples de verificar. Entretanto, quando todos os módulos passaram a trabalhar simultaneamente, pequenas diferenças de configuração começaram a causar comportamentos incorretos.

Uma das primeiras dificuldades ocorreu durante a implementação da seleção entre o simulador e o ESP32 real. Inicialmente, alterar a opção apresentada na interface não significava necessariamente que o backend estava utilizando a mesma fonte. Dessa forma, em algumas situações o dashboard indicava que o ESP32 real estava selecionado enquanto a API ainda considerava o simulador como dispositivo ativo.

Para solucionar esse problema foi criada uma lógica específica de seleção da fonte através da API. A partir dessa alteração, as interfaces passaram a consultar e modificar a fonte ativa diretamente no backend. Foram utilizados identificadores diferentes para cada dispositivo, permitindo distinguir \texttt{esp32-001} de \texttt{esp32-simulator-001}.

Essa alteração também resultou em um mecanismo de proteção contra dados provenientes do dispositivo incorreto. Quando o backend recebe determinadas requisições de um dispositivo diferente daquele atualmente selecionado, a operação pode ser rejeitada. Durante os testes esse comportamento apareceu através de respostas HTTP de conflito, o que inicialmente parecia indicar uma falha de comunicação, mas na realidade mostrava que a seleção de fonte estava funcionando.

Outra dificuldade encontrada esteve relacionada aos endereços utilizados para comunicação com a API. Durante o desenvolvimento no próprio computador, alguns testes foram realizados utilizando o endereço local \texttt{127.0.0.1}. Entretanto, esse endereço representa a própria máquina que realiza a requisição e não pode ser utilizado pelo ESP32 para acessar o servidor executado em outro equipamento.

Foi necessário, portanto, configurar o ESP32 e as demais aplicações utilizando o endereço de rede correspondente ao servidor. A padronização desses endereços foi importante para evitar situações em que a interface Web funcionava corretamente no computador, mas o dispositivo físico não conseguia alcançar a API.

A integração com o ESP32 real também apresentou dificuldades que não apareciam durante a utilização do simulador. Enquanto o simulador dependia apenas dos programas executados no computador, o dispositivo físico dependia também da conexão Wi-Fi, intensidade do sinal, configuração correta do endereço do servidor e disponibilidade da API.

Durante essa etapa, a análise das respostas HTTP fornecidas pelo servidor foi importante para diferenciar problemas de conexão de erros relacionados à lógica da aplicação. A observação das requisições recebidas pelo backend também permitiu verificar se o ESP32 estava enviando telemetria e consultando corretamente o estado do LED.

A implementação do OTA apresentou outra dificuldade durante o desenvolvimento. Apesar de o dispositivo estar conectado à rede e executar corretamente o firmware, a identificação automática através do nome configurado depende do funcionamento adequado dos serviços de descoberta na rede. Em algumas situações o dispositivo não aparecia imediatamente como uma opção disponível para programação.

Após a configuração e os testes necessários, foi possível realizar a atualização do firmware pela rede. Essa funcionalidade facilitou consideravelmente as alterações posteriores, pois eliminou a necessidade de manter o dispositivo permanentemente conectado através do cabo utilizado para programação.

Também foi possível observar a vantagem da utilização de uma API como ponto central do sistema. Durante o desenvolvimento foram utilizadas duas interfaces diferentes, Node-RED e uma aplicação Web, além de duas fontes de dados, o simulador e o ESP32. Mesmo assim, não foi necessário desenvolver uma estrutura de comunicação completamente diferente para cada combinação, pois todos os módulos utilizavam a API como elemento intermediário.

De maneira geral, as maiores dificuldades não estiveram na leitura individual do sensor ou no acionamento do LED, mas na integração e sincronização de todos os elementos. Essa etapa permitiu compreender melhor problemas que aparecem em sistemas distribuídos, principalmente aqueles relacionados à identificação dos dispositivos, endereçamento de rede, disponibilidade dos serviços e consistência das informações apresentadas ao usuário.
