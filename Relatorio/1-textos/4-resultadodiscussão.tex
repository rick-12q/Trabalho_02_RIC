\section{Dificuldades e impressões}
%\addcontentsline{toc}{chapter}{Resultados e discussões}

%%======%%======%0%======%%=======%%

%===%===%
%\vspace{1cm}
%===%===%
Durante todo o processo de construção do projeto, algumas dificuldades foram enfrentadas, dentre elas a seleção da fonte de dados (ESP32 Real ou simulador). A questão é que mudar a fonte de dados no frontend não implica, necessariamente, alterar a fonte utilizada pelo backend. Para solucionar esse problema, foi necessária a implementação de uma lógica de seleção da fonte ativa, garantindo que os dados apresentados e armazenados correspondessem ao dispositivo selecionado pelo usuário.

Além disso, outro ponto que exigiu atenção foi a integração do Node-RED com a API. Como o Node-RED, o frontend, o simulador e o ESP32 realizam requisições ao backend, foi necessário garantir que todos utilizassem o mesmo endereço da API e a mesma identificação do dispositivo ativo. Durante os testes, diferenças entre o endereço utilizado localmente (\texttt{127.0.0.1}) e o endereço utilizado pelo ESP32 na rede fizeram com que diferentes componentes não apresentassem o mesmo estado da aplicação. A padronização do acesso ao backend foi, portanto, fundamental para manter a comunicação consistente entre os diferentes módulos.

A implementação da comunicação com o ESP32 real também apresentou dificuldades adicionais em relação ao simulador. Enquanto o simulador executado no computador possui acesso direto aos serviços locais, o ESP32 depende da comunicação pela rede Wi-Fi. Dessa forma, foi necessário verificar aspectos como o endereço IP do servidor, a disponibilidade da porta utilizada pela API e a conectividade entre o microcontrolador e o computador. Os códigos de resposta HTTP fornecidos pela API foram particularmente úteis durante essa etapa, permitindo identificar situações em que a comunicação estava ocorrendo, mas a requisição era rejeitada por incompatibilidade entre o dispositivo e a fonte de dados selecionada.

Outro aspecto importante foi a implementação da atualização remota do firmware por meio de OTA (\textit{Over-the-Air}). Essa funcionalidade exigiu que o ESP32 estivesse corretamente conectado à rede e pudesse ser identificado pelo computador antes do envio de uma nova versão do firmware. Apesar das dificuldades iniciais de configuração e detecção do dispositivo pela rede, o recurso mostrou-se especialmente útil por permitir futuras alterações no firmware sem a necessidade de conexão física direta ao microcontrolador.

De maneira geral, as dificuldades encontradas durante o desenvolvimento contribuíram para uma melhor compreensão da integração entre sistemas embarcados, aplicações web e serviços de backend. Os testes realizados ao longo do desenvolvimento foram, portanto, essenciais para identificar problemas de comunicação e tornar a aplicação mais integrada e confiável.
